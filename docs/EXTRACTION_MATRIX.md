## 6. What stays in the WakoLab frontend

API ports and calls, session and authentication, capabilities, catalog contracts and state, routes, i18n catalogs and locales, the appearance preference key, the `agent`/`human` identity colours and icons, registration and profile pages, the prototype, product tests and the bundle budget. The frontend later consumes a system the way any external project would (tracked separately in [WakoLab/wakolab-front#16](https://github.com/WakoLab/wakolab-front/issues/16)).

## 7. Duplication and drift

Three repositories will hold copies of the same primitives. That is the accepted model.
- Each copied file keeps a provenance header with the source path and commit.
- A fix found in one system is proposed to the others by an issue in each repository; no automatic synchronization.
- Systems may diverge on purpose.

## 8. Order and rollback

1. Console first (Console #1), then the frontend consumes it (front#16), then Folio and Marquee reuse the method.
2. Each extraction is one reviewed pull request in one system repository. Rollback means reverting that pull request; no other repository is affected.
3. The frontend pins a system by commit; rollback means re-pinning the previous commit.

Essential versus optional: the copies, the adaptations above and the independence check are required. New motion, new states, DTCG tooling and other redesigns are optional, not prerequisites.
